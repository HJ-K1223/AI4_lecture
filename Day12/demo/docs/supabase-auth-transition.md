# Supabase Auth 전환 및 로컬 검증 안내

## 현재 상태

2026-10-30 기준 **로그인 자체의 Auth 전환은 아직 적용하지 않았습니다.** 사용자 지정 공유 파일 `C:/AI4/.env`에서 프로젝트 URL과 Publishable key를 읽어 실제 Auth 설정 API 접근을 확인했습니다. 계정·세션·데이터는 변경하지 않았습니다. 기존 로그인과 구매 기능을 유지하며 비밀값은 출력하지 않았습니다.

환경설정은 공유 파일을 먼저 읽고 프로젝트 `.env`를 나중에 읽습니다. 같은 키는 프로젝트 설정이 우선하고, 프로세스 환경변수는 두 파일보다 우선합니다. 공유 파일을 수정하거나 키를 복제하지 않았습니다.

```powershell
Set-Location C:\AI4\Day12\demo
.\.venv\Scripts\python.exe -m app.core.check_supabase_auth
```

위 명령은 Auth API 접근 확인이며 사용자 로그인·토큰 갱신·권한 전환의 완료 검증은 아닙니다.

사용자는 테스트 계정이므로 Auth에 새로 가입하는 방식을 선택했습니다. 기존 회원·구매내역은 삭제하지 않고 보존합니다. 기존 Argon2 비밀번호 해시를 현재 방식 그대로 Supabase Auth 로그인에 사용할 수는 없습니다. 이메일 문자열만 일치한다고 기존 회원과 자동 연결하지 않습니다.

## 적용할 구조

- Supabase Auth가 가입·이메일 확인·로그인·로그아웃·토큰 갱신을 담당합니다.
- shoppingmall.members는 이름·연락처·주소·탈퇴 상태 등 쇼핑몰 프로필을 담당합니다. Auth UUID를 별도 유일한 FK로 연결하고 기존 회원·주문 ID는 보존합니다.
- 브라우저는 FastAPI만 호출합니다. Auth 토큰을 localStorage나 읽을 수 있는 서명 쿠키에 담지 않습니다.
- 서버 보관 세션에 토큰을 보관하고 브라우저에는 추측 불가능한 세션 ID를 HttpOnly·Secure·SameSite=Lax 쿠키로 전달하는 방식을 적용합니다. 저장 토큰 암호화·동시 갱신 잠금·폐기를 함께 구현해야 합니다.
- 서버는 Auth 사용자 검증 결과와 members의 활성 상태·권한을 함께 확인합니다. JWT 내용을 단순 디코딩한 결과는 신뢰하지 않습니다.
- 기존 CSRF와 내부 next 검증·401 복귀 규칙을 유지합니다.
- PostgreSQL 직접 연결은 사용자의 JWT를 자동으로 RLS에 전달하지 않습니다. 서버의 소유권 검사는 계속 필수입니다. DB 전용 최소 권한 역할과 트랜잭션의 사용자 컨텍스트를 통한 RLS 추가 방어를 구현·검증합니다. 테이블 소유자 연결만으로 RLS가 보호된다고 설명하지 않습니다.

| 대상 | 비회원 | 일반 회원 | 관리자 |
| --- | --- | --- | --- |
| 활성 상품 목록·상세 | 허용 | 허용 | 허용 |

| 구매내역·주문 상세 | 로그인 요구 | 본인만 | 명시된 관리 API에만 별도 권한 |
| 회원정보·비밀번호·탈퇴 | 로그인 요구 | 본인만·민감 작업 재인증 | 타인의 비밀번호 조회·변경 불가 |

관리자 화면이나 임의 주문 변경 기능은 이번 전환만으로 추가하지 않습니다. 기존 기능에 소유권을 적용하고 관리 작업용 권한 기반을 분리합니다. 관리자 승격은 브라우저 가입 입력이나 수정 가능한 user_metadata로 허용하지 않습니다. 서버가 관리하는 역할을 기준으로 합니다. 미인증은 401, 권한 부족은 403, 타인 리소스는 404를 기본으로 합니다.

## 사용자에게 필요한 준비

1. 기존 계정은 구매내역을 유지하며 비밀번호 재설정으로 연결할지, 테스트 계정이므로 Auth에 새로 가입할지 선택합니다. 기존 데이터 삭제는 자동으로 하지 않습니다.
2. Supabase 프로젝트 설정의 프로젝트 URL과 Publishable key 또는 기존 anon key를 **로컬 .env에만** 추가합니다. 아래 값은 예시이며 실제 값을 문서·채팅에 붙이지 않습니다.

```dotenv
SUPABASE_URL=https://YOUR_PROJECT.supabase.co
SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLISHABLE_KEY
```

이 두 변수의 애플리케이션 지원은 전환 구현 시 추가합니다. DB 비밀번호만으로는 Auth HTTP 로그인 설정이 완성되지 않습니다. service_role·Secret key는 일반 로그인용으로 요구하지 않습니다.

3. Auth 이메일 확인 여부와 발송 설정을 확인합니다. 이메일을 확인하지 않은 사용자에게 프로필 연결이나 로그인 권한을 부여하지 않도록 구현합니다. 테스트 편의를 위해 운영 이메일 확인을 임의로 끄지 않습니다.
4. 이메일 확인·재설정 콜백 주소는 구현할 실제 경로가 확정된 뒤 Supabase 허용 Redirect URL에 등록합니다. 현재 존재하지 않는 콜백 경로를 완료된 기능처럼 안내하지 않습니다.

## 지금 실행할 수 있는 명령

프로젝트 폴더를 VS Code로 열고 PowerShell에서 실행합니다.

```powershell
Set-Location C:\AI4\Day12\demo
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m app.core.check_db
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --port 8012
```

[현재 홈페이지](http://127.0.0.1:8012/products)를 엽니다. 이미 같은 포트의 서버가 실행 중이면 추가 서버를 실행하지 않습니다. 종료는 해당 터미널의 Ctrl+C입니다. APP_BASE_URL은 실제 포트와 일치해야 합니다.

위 명령은 **현재 자체 인증 버전**의 실행·회귀 검증 명령입니다. Supabase Auth 검증 완료를 의미하지 않습니다. 전환 후 Auth 전용 테스트 명령·이메일 콜백 절차를 이 문서에 추가합니다.

## 전환 후 확인할 시나리오

- 이메일 확인·가입·로그인·로그아웃과 내부 next 복귀
- 만료 토큰 갱신·동시 갱신·폐기된 세션 재사용 거부
- A 회원이 B 회원의 장바구니·주문·결제·회원정보에 접근할 수 없음
- 일반 회원이 요청 본문·사용자 메타데이터를 조작해 관리자로 승격할 수 없음
- 권한 변경·탈퇴 후 기존 토큰으로 접근할 수 없음
- PostgreSQL 서버 역할에서도 RLS 우회 여부를 실제로 확인
- 기존 구매·재고 동시성·중복 결제 테스트 유지
