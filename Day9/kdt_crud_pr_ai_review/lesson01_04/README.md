# FastAPI로 간단한 방명록 API 만들기

방문자의 이름과 메시지를 저장하고, 조회·수정·삭제하는 CRUD 예제입니다.
초기 데이터는 제공된 코드와 같습니다.

```json
[{"id": 1, "name": "홍길동", "message": "안녕하세요"}]
```

## 실행 방법

Python 3.10 이상, Pydantic 2 버전을 사용합니다. CMD에서 실행하세요.

```bat
cd /d C:\AI4\Day9\kdt_crud_pr_ai_review\lesson01_04
python -m pip install "fastapi>=0.115,<1" "pydantic>=2,<3" "httpx>=0.27,<1" "uvicorn>=0.30,<1"
python check.py
```

`check.py`는 TestClient로 `main.py`의 앱을 직접 호출합니다. 서버를 따로 켤 필요는 없습니다.
검증마다 새 Python 프로세스로 실행하세요. `python -O`는 assert 검사를 생략하므로 사용하지 않습니다.

서버를 직접 실행하려면 다음 명령을 사용합니다.

```bat
python -m uvicorn main:app --reload
```

브라우저의 API 문서: <http://127.0.0.1:8000/docs>

## API와 요청 규칙

| 작업 | 요청 | 정상 응답 | 요청 본문 |
|---|---|---|---|
| 등록 | POST /tasks | 201, 생성한 방명록 | name, message 모두 필수 |
| 전체 조회 | GET /tasks | 200, 방명록 목록 | 없음 |
| 개별 조회 | GET /tasks/{task_id} | 200, 해당 방명록 | 없음 |
| 전체 수정 | PUT /tasks/{task_id} | 200, 수정한 방명록 | name, message 모두 필수 |
| 부분 수정 | PATCH /tasks/{task_id} | 200, 수정한 방명록 | name 또는 message, 또는 둘 다 |
| 삭제 | DELETE /tasks/{task_id} | 204, 본문 없음 | 없음 |

등록·전체 수정 요청 예시:

```json
{"name": "김방문", "message": "반갑습니다"}
```

메시지만 부분 수정하는 요청 예시:

```json
{"message": "다시 방문했어요"}
```

이름과 메시지는 문자열이며 각각 최소 한 글자입니다.
누락된 필수값, 빈 문자열, 명시적인 null은 422로 응답합니다.
PATCH의 빈 객체 `{}`는 아무것도 바꾸지 않고 현재 방명록을 반환합니다.

ID는 1 이상의 정수로 서버가 자동 발급합니다. 요청 본문에서 ID를 입력하거나 수정할 필요가 없습니다.
제공된 코드의 `TaskPut.id`는 서버 관리라는 목적에 맞춰 입력 모델에서 제외했습니다.
경로의 `task_id`로 수정 대상을 지정하고, PUT과 PATCH는 이름과 메시지만 수정합니다.
정의하지 않은 추가 필드는 Pydantic 기본 동작에 따라 무시됩니다. 본문의 id도 반영되지 않습니다.

## 문제 원인과 해결 코드

### 삭제한 ID를 다시 사용하지 않기

현재 리스트의 최대 ID에 1을 더하면, 최대 ID 삭제 후 이전 번호를 다시 사용할 수 있습니다.
`last_issued_id`는 시작할 때 초기 데이터의 최대 ID로 한 번만 설정합니다.
그 뒤에는 등록할 때만 증가시키고 삭제할 때는 줄이지 않습니다.
초기 데이터가 바뀌어도 반복문으로 최대 ID를 찾으므로 특정 번호에 의존하지 않습니다.

등록 코드의 `with create_lock:`은 동시에 들어온 등록 요청을 같은 프로세스 안에서 하나씩 처리합니다.

### 없는 ID는 404로 응답하기

`find_task()`가 각 항목의 id를 비교하고, 없으면 `HTTPException`으로 404를 반환합니다.
개별 조회·PUT·PATCH는 이 함수를 사용합니다. DELETE도 못 찾으면 동일하게 응답합니다.
빈 목록을 전체 조회하는 것은 정상 조회이므로 200과 빈 리스트를 반환합니다.
입력 본문이 잘못된 경우에는 경로 처리 전에 FastAPI가 422를 반환할 수 있습니다.

### PATCH에서 다른 값 보존하기

기본 `model_dump()`는 생략된 필드의 기본값까지 포함해 기존 데이터를 덮어쓸 수 있습니다.
`model_dump(exclude_unset=True)`는 요청에 명시된 필드만 추출합니다.
이름만 수정하면 메시지가 유지되고, 메시지만 수정하면 이름이 유지됩니다.

`TaskPatch`의 None 기본값은 필드 생략을 표현합니다.
명시적인 null은 `changes`의 값을 반복문으로 검사해서 거절합니다.
모든 값을 확인한 뒤에 `task.update(changes)`를 호출하므로 일부 값만 먼저 바뀌는 문제도 막습니다.

### ID와 리스트 위치 구분하기

ID는 고유 번호이고 인덱스는 현재 리스트에서의 위치입니다. 삭제하면 위치만 달라집니다.
조회·수정에서는 `task["id"] == task_id`로 대상을 찾습니다.
삭제에서는 `enumerate(tasks)`로 위치와 항목을 함께 꺼내 ID로 대상을 찾은 뒤,
`tasks.pop(index)`로 삭제합니다. `tasks.pop(task_id)`처럼 ID를 위치로 쓰지 않습니다.

## 검증 내용

- 초기 데이터 전체·개별 조회
- 이름·메시지를 받아 정상 등록하고 201 응답, 한 글자 입력 허용
- PUT으로 이름과 메시지를 모두 수정하면서 ID 유지
- PATCH로 이름만·메시지만·둘 다 수정, 생략한 값과 ID 유지
- 빈 PATCH에서 기존 값 유지
- POST·PUT의 필수값 누락, 빈 문자열, null을 422로 거절
- PATCH의 빈 문자열, null을 422로 거절하고 기존 데이터 보존
- 유효한 이름과 null 메시지를 함께 PATCH해도 일부 값만 변경되지 않음
- 중간 방명록 삭제 시 다른 항목 보존, 204 응답 본문 없음
- 없는 ID에 개별 GET·PUT·PATCH·DELETE 모두 404 응답
- 삭제로 위치가 달라진 방명록을 ID로 조회·수정
- 최대 ID 삭제 및 전체 삭제 이후에도 발급한 ID 재사용 방지

테스트는 API에서 반환받은 ID를 사용하고, 없는 ID는 실제 삭제한 ID를 사용합니다.
특정 ID만 통과시키는 분기, 오류 무시, 검사를 건너뛰는 코드는 없습니다.
상태 코드·최소 길이·초기 데이터는 요구사항에서 정한 값입니다.
미사용 기능이나 다른 차시 기능은 추가하지 않았습니다.

## 남은 한계

- 메모리에만 저장하므로 재시작하면 데이터와 ID 발급 이력이 초기화됩니다.
  재시작 이후까지 보장하려면 DB 등에 발급 상태를 저장해야 합니다.
- 여러 서버 프로세스는 데이터와 카운터를 공유하지 않습니다. Lock도 프로세스 내부에서만 동작합니다.
- 최소 길이만 검사하므로 공백 한 글자도 허용합니다.

## 실제로 수행하지 않는 검증

check.py는 순차 요청으로 검증합니다. 동시 요청·부하 테스트, 여러 프로세스,
실제 네트워크·브라우저, 재시작 후 영속성, DB 연동은 검증하지 않습니다.
