사용자가 v2 구현 계획을 승인하고 코드 생성·테스트를 요청하여 구현했습니다. v3는 승인 범위를 바꾸는 새 제안이 아니라 실제 작업 결과를 반영한 기록입니다. 실행 코드는 프로젝트 아래에 있으며, 실행·배포 방법은 최신 공식 자료를 확인해 [README](README.md)에 정리했습니다. 실제 alwaysdata 계정 배포는 수행하지 않았습니다.

## 1. 구현 범위

현재 구현할 기능은 이메일 회원가입, 로그인·로그아웃, 비밀번호 찾기 Mock, 제목·본문 기반 게시판, 제목만 표시하는 목록과 기본 10개 페이징, 상세 조회, 본인 글 수정·삭제, 댓글, 불쾌한 표현 마스킹, 관리자 금칙어 추가·삭제입니다.

alwaysdata Free에 배포할 수 있는 설정, 배포 안내와 배포 후 검증 계획을 현재 범위에 포함합니다. 이 문서 수정 작업에서는 실제 계정 연결·업로드·배포를 수행하지 않습니다.

실제 SNS 연동, 실제 비밀번호 복구/메일 발송, 회원 탈퇴, 대댓글, 댓글 수정, 검색, 첨부파일, 알림은 이번 범위에서 제외합니다. 게시글 작성과 댓글 작성·조회·본인 삭제는 원문의 게시판/댓글 기능을 구체화하기 위한 제안입니다.

## 2. 기술 스택과 정책 제안

배포 대상 **alwaysdata Free는 사용자 확정 사항**입니다. 아래 기술·기능 정책은 해당 환경을 기준으로 정리한 **v2 설계안**이며 기능 관련 가정은 사용자 피드백으로 수정할 수 있습니다.

| 항목 | 추천안 | 이유와 영향 |
| --- | --- | --- |
| 백엔드 | Python + Django | 회원 인증·폼·ORM 기능을 활용하는 단일 애플리케이션 구성 |
| 프론트엔드 | Django Templates + 기본 CSS | 별도 프론트 서버·Node 빌드 없이 구성 |
| DB | alwaysdata 관리형 PostgreSQL | 기존 ERD 유지. 서버 직접 설치 없이 관리 화면에서 DB/사용자 구성 |
| 웹 실행 | alwaysdata Python WSGI 사이트 | 플랫폼 관리 uWSGI 사용. 앱에서 Gunicorn/uWSGI를 별도 설치하지 않음 |
| 정적 파일 | collectstatic + WhiteNoise 미들웨어 | 단일 WSGI 사이트에서 작은 CSS 제공, 별도 웹 서버 불필요 |
| 버전 | 계정 지원 Python과 Django·드라이버의 호환 버전 확인 후 고정 | CLI/venv/WSGI 버전을 일치시킴 |
| 인증 | DB 세션 + HttpOnly/SameSite 쿠키 | 운영은 HTTPS/Secure, 로그아웃 시 세션 무효화. Redis 불필요 |
| 비밀번호 | 현재부터 Django 비밀번호 해시 적용 | 원문의 ‘향후 암호화’에 대한 보안 보완 제안. 평문 저장하지 않음 |
| 조회 권한 | 목록·상세·댓글은 로그인한 회원만 조회 | 작성·수정·삭제에는 로그인 필요 |
| 댓글 범위 | 작성·조회·본인 삭제 | 댓글 수정·대댓글 제외 |
| 삭제 방식 | 물리 삭제 | 게시글 삭제 시 댓글도 삭제. 작성자가 있는 회원 삭제는 제한 |
| 마스킹 시점 | 원문 저장 후 조회 시 마스킹 | 금칙어 변경이 기존 글에도 반영됨. 원문 접근 통제 필요 |
| 마스킹 대상 | 제목·본문·댓글 | 닉네임은 현재 제외 |
| 탐지 방식 | 정규화한 키워드 부분 일치 | 원문에서 허용한 키워드 방식 채택. REGEX는 현재 미지원 |
| 관리자 | members.role의 ADMIN | 일반 가입은 USER 고정. 별도 초기화 명령으로 관리자 생성 |

Django는 커스텀 회원 모델과 인증 구성을 지원합니다. 이메일 기반 회원 모델은 첫 마이그레이션 전에 정의하는 방향으로 계획합니다. [Django 공식 인증 커스터마이징 문서](https://docs.djangoproject.com/en/6.0/topics/auth/customizing/)

## 4. 데이터 모델 적용 계획

기준 ERD, 컬럼, 인덱스, 삭제 관계는 [설계 프롬프트의 8절](ai_agent_design_prompt.md#8-데이터-모델-초안--mermaid-erd)을 따릅니다. 다음은 v2의 구현 구체화 사항입니다. PostgreSQL이 지원되므로 DB 종류와 ERD를 바꿀 필요는 없습니다.

| 모델 | 주요 제약과 관계 | 구현 시 반영 |
| --- | --- | --- |
| Member → members | 정규화 email UNIQUE, nickname 필수, role USER/ADMIN | 이메일 앞뒤 공백 제거·소문자화 후 가입/로그인. 닉네임 중복 허용 |
| Post → posts | author_id NOT NULL FK, title 200자, content 20,000자 | 작성자는 인증 정보로 지정. 목록 인덱스 `(created_at DESC, id DESC)` |
| Comment → comments | post_id/author_id NOT NULL FK, content 1,000자 | 게시글별 `(post_id, created_at, id)` 인덱스, 작성자 인덱스 |
| BannedTerm → banned_terms | UNIQUE(match_type, pattern), created_by NULL 허용 | CHECK도 KEYWORD만 허용. 등록자 인덱스, 출처 필드 유지 |

- PK는 자동 생성 BIGINT, 작성 시각은 시간대가 있는 값으로 저장합니다.
- 회원 모델은 Django의 해시 처리와 호환되게 설계합니다. 프레임워크 필드 `password`의 물리 컬럼을 ERD의 `password_hash`로 매핑하고, 필요한 `is_active`, `last_login` 등 인증 지원 필드는 마이그레이션 명세에 추가 사유를 기록합니다.
- 별도 Django 관리자 사이트는 현재 사용하지 않고 금칙어 전용 관리 화면을 만듭니다. 앱 관리자 판정은 `role`로 통일합니다.
- 회원 삭제는 게시글·댓글 참조가 있으면 거부하고, 게시글 삭제는 댓글을 연쇄 삭제합니다. 금칙어 등록 회원이 삭제되면 `created_by`만 NULL로 변경합니다.
- ORM의 삭제 정책과 실제 DB FK 동작을 구분해 확인합니다. DB 수준 CASCADE/SET NULL이 기준 ERD대로 동작하도록 필요한 마이그레이션을 작성하고 직접 DB 삭제도 검증합니다.
- 제목·본문·댓글·닉네임·패턴에 빈 값/공백 제약과 길이 검증을 적용합니다. role/match_type의 허용값은 DB CHECK로도 제한합니다.
- Django 세션용 테이블은 기술 지원 테이블로 추가합니다. `clearsessions` 정리 절차를 운영 문서에 포함하고 Redis 의존성을 두지 않습니다.

## 5. 화면과 HTTP 엔드포인트

서버 렌더링 구조이므로 JSON API를 중복 구축하지 않습니다. GET은 화면 조회, POST는 CSRF 검증이 있는 폼 처리로 구성합니다.

| 화면/동작 | 경로 | 메서드 | 권한·결과 |
| --- | --- | --- | --- |
| 회원가입 | /accounts/signup/ | GET, POST | 비로그인, 성공 후 로그인 화면 이동 |
| 로그인 | /accounts/login/ | GET, POST | 비로그인, 성공 후 게시판 이동 |
| 로그아웃 | /accounts/logout/ | POST | 로그인, 세션 무효화 후 목록 이동 |
| 비밀번호 찾기 Mock | /accounts/password-help/ | GET, POST | 공개, 항상 동일한 Mock 안내. 메일/토큰/변경 없음 |
| 게시글 목록 | /posts/?page=1 | GET | 로그인, 마스킹 제목과 페이지 탐색 표시 |
| 게시글 작성 | /posts/new/ | GET, POST | 로그인 |
| 게시글 상세 | /posts/{id}/ | GET | 로그인, 제목·본문·댓글 마스킹 |
| 게시글 수정 | /posts/{id}/edit/ | GET, POST | 작성자만, 편집용 원문 제공 |
| 게시글 삭제 | /posts/{id}/delete/ | POST | 작성자만 |
| 댓글 작성 | /posts/{id}/comments/ | POST | 로그인 |
| 댓글 삭제 | /comments/{id}/delete/ | POST | 댓글 작성자만 |
| 금칙어 목록/추가 | /moderation/terms/ | GET, POST | ADMIN만 |
| 금칙어 삭제 | /moderation/terms/{id}/delete/ | POST | ADMIN만 |

본인 글 편집 GET의 원문 접근은 작성자 권한 검증 후에만 허용하고 응답은 `Cache-Control: no-store`로 설정합니다. 관리자에게 타인 글 수정·삭제 권한을 추가하지 않습니다.

입력 이름은 회원가입 `email/nickname/password/password_confirm`, 로그인 `email/password`, 게시글 `title/content`, 댓글 `content`, 금칙어 `pattern`으로 정합니다. 작성자 ID·role·created_by는 클라이언트에서 받지 않습니다.

성공한 POST는 303 리다이렉트로 중복 제출을 줄입니다. 입력 오류는 400과 필드 오류, 로그인 실패는 400과 계정 존재 여부를 구별하지 않는 안내, 권한 부족은 403, 없는 리소스는 404로 처리합니다. 비로그인 상태의 보호 화면 접근은 로그인 화면으로 이동하며, 이동 목적지는 내부 경로만 허용합니다. 서버 오류는 일반 안내만 표시하고 민감정보는 응답하지 않습니다.

## 6. 핵심 동작 확정안 — 검토 대상

### 6.1 페이징과 댓글

- 페이지 번호는 1부터 시작하고 페이지 크기는 10으로 고정합니다. `size` 변경 옵션은 제공하지 않습니다.
- 게시글은 `created_at DESC, id DESC`로 정렬합니다.
- 데이터가 없으면 1페이지에서 빈 목록을 표시합니다. 0·음수·비정수 page는 400, 존재하는 마지막 페이지를 초과하면 404로 처리합니다.
- 댓글은 `created_at ASC, id ASC`로 정렬하고 상세 화면에서 기본 20개씩 페이징합니다. `comment_page`는 1부터 시작하며 비정수/0/음수는 400, 범위 초과는 404로 처리합니다. 댓글이 없으면 1페이지는 빈 목록입니다. 기존 전체 조회안을 무료 자원에 맞춰 제한하며 누락된 댓글은 페이지 이동으로 확인합니다.

### 6.2 마스킹

- 저장 원문은 유지합니다. 목록·상세·댓글 표시용 출력에서 마스킹한 뒤 HTML 이스케이프합니다. 사용자 HTML은 허용하지 않습니다.
- 키워드는 NFKC 정규화와 대소문자 정규화를 적용해 비교합니다. 공백/특수문자 삽입·자모 분리 등 모든 우회를 탐지하는 기능은 이번 범위에서 제외합니다.
- 정규화로 문자열 길이가 달라질 수 있으므로 정규화 문자열과 원문 위치 간 매핑을 만들어 일치한 원문 구간을 치환합니다. 합성 문자와 호환 문자 사례를 테스트합니다.
- 겹치거나 포함되는 일치 구간은 합쳐서 구간마다 `***` 한 번으로 치환합니다. 치환 결과를 다시 탐지하지 않습니다.
- 금칙어는 정규화 후 중복 판정합니다. 한 단어가 다른 단어 안에 포함되는 경우도 탐지하므로 오탐 가능성을 관리자 화면에서 안내합니다.
- v2에서는 캐시를 두지 않고 요청마다 규칙을 한 번 읽어 재사용합니다. 변경 커밋 이후 시작한 조회부터 최신 규칙을 적용합니다. 목록에서는 본문을 읽지 않고 제목에만 적용하며, 댓글은 현재 페이지의 데이터만 마스킹합니다.
- REGEX 유형 등록은 거부하고 DB CHECK도 KEYWORD로 제한합니다. 향후 REGEX 도입 시 ERD·마이그레이션·실행 제한·유효성 검증을 함께 변경합니다.

### 6.3 금칙어 초기 데이터

- 공개 사전 항목과 이용 조건을 확인해 데모 키워드 2개를 독립 선정했습니다. 포괄적인 운영 목록은 아니며, 출처와 한계를 `docs/seed_sources.md`에 기록했습니다.
- `seeds/banned_terms.json`에 규칙/유형/출처 정보를, `docs/seed_sources.md`에 제목·URL·조회일·선정 근거·한계를 기록합니다.
- 적절한 재사용 근거를 확인하지 못하면 테스트용 예시로 한정하고 그 한계를 표시합니다. 최신 운영 목록으로 표현하지 않습니다.
- seed 로더는 동일 키의 기존 규칙을 건너뛰는 방식으로 반복 실행에 대응합니다. 관리자 삭제 후 자동으로 재등록되지 않도록 seed는 자동 시작이 아닌 명시적인 초기화 명령으로만 실행합니다.

## 8. 실행 환경과 검증 계획

### 로컬 준비 및 실행 순서

1. 사용자 승인 후 Python/PostgreSQL 설치 상태와 호환 버전을 확인합니다. 없는 의존성 설치는 환경의 승인 정책을 따릅니다.
2. 프로젝트 내부 `.venv`와 의존성 파일을 구성합니다. Django, PostgreSQL 드라이버, WhiteNoise 등 실제 사용하는 최소 패키지만 고정하고 개발 도구는 운영 requirements에서 분리합니다.
3. `.env.example`을 기준으로 로컬 환경을 설정하고 개발 전용 DB/사용자를 준비합니다. 비밀키·비밀번호는 예제 파일에 넣지 않습니다.
4. `python manage.py migrate`로 스키마를 구성하고 설정 검사 및 DB 제약을 검증합니다.
5. 구현 예정인 `python manage.py create_admin` 명령으로 비밀번호를 숨김 입력받아 관리자를 생성합니다. 기본 관리자 비밀번호를 하드코딩하지 않습니다.
6. 구현 예정인 `python manage.py load_banned_terms seeds/banned_terms.json` 명령으로 검토한 초기 규칙을 등록합니다.
7. `python manage.py test`로 테스트하고 `python manage.py runserver`로 로컬 화면을 확인합니다.

위 명령은 실행 계획이며 현재 실행하거나 성공을 확인한 결과가 아닙니다. 최종 README에는 실제 구현한 명령과 설치·접속 방법을 기록합니다.

### alwaysdata 배포 순서

아래 `<account>`와 접속 정보는 미확정 자리표시자입니다. 경로는 계획값이며 배포 시 실제 등록값과 맞춥니다. Windows 로컬 `.venv`나 로컬 DB를 서버에 복사하지 않습니다.

1. Free 계정과 실제 할당량, SSH 접근, Python/PostgreSQL 버전을 확인합니다. 웹 주소는 `https://<account>.alwaysdata.net`을 사용합니다.
2. 관리 화면 `Databases > PostgreSQL`에서 앱 전용 DB와 사용자를 구성합니다. 호스트는 화면의 실제 값(통상 `postgresql-<account>.alwaysdata.net`), 포트는 5432를 사용하며 `localhost`로 고정하지 않습니다. DB 권한은 앱 스키마 마이그레이션에 필요한 범위로 설정합니다.
3. 소스와 잠금된 의존성 명세만 SSH/SFTP 등으로 `/home/<account>/apps/note-demo`에 전송합니다. `.git`, `.venv`, 비밀 파일, 테스트 산출물, 로그, DB 덤프는 배포 대상에서 제외합니다.
4. 서버의 Python 선택을 맞춘 뒤 `python -m venv /home/<account>/venvs/note-demo`로 생성하고 활성화합니다. `python -m pip install --no-cache-dir -r requirements.txt`를 실행합니다. 플랫폼의 uWSGI를 중복 설치하지 않습니다.
5. 관리 화면의 사이트 환경변수에 비밀키·운영 설정 모듈·DB 접속값·호스트를 설정합니다. SSH에서 실행하는 관리 명령에도 같은 환경변수를 별도로 전달합니다. 사이트 설정이 SSH 셸에 자동 공유된다고 가정하지 않습니다.
6. 운영 설정에서 `DEBUG=False`, 정확한 `ALLOWED_HOSTS`, HTTPS 출처의 `CSRF_TRUSTED_ORIGINS`, Secure 세션/CSRF 쿠키를 적용합니다. alwaysdata는 `X-Forwarded-Proto`를 전달하므로 해당 신뢰 경계를 확인한 뒤 `SECURE_PROXY_SSL_HEADER`를 구성하고 HTTPS 강제 이동을 점검합니다. [플랫폼 HTTP 스택](https://help.alwaysdata.com/en/docs/web-hosting/sites/http-stack/)
7. 초기에는 빈 운영 DB에 `python manage.py migrate`를 실행합니다. 이후 갱신 시에는 변경 전에 외부로 DB 백업을 확보하고, 필요하면 유지보수 안내 후 마이그레이션합니다. DB 초기화나 테스트 데이터 덮어쓰기는 하지 않습니다.
8. 관리자/검토된 seed를 명시적 명령으로 초기화하고 `python manage.py collectstatic --noinput`으로 `STATIC_ROOT=/home/<account>/apps/note-demo/staticfiles`에 수집합니다. `STATIC_URL=/static/`와 WhiteNoise 미들웨어로 제공하며, 수집 폴더에 비밀 파일을 넣지 않습니다. [Django 정적 배포 절차](https://docs.djangoproject.com/en/6.0/howto/static-files/deployment/)
9. `Web > Sites`에 **Python WSGI** 사이트를 등록합니다. 앱 경로는 `/home/<account>/apps/note-demo/config/wsgi.py`, 작업 폴더는 프로젝트 루트, venv는 4단계 경로로 설정하고 일치하는 Python 버전을 선택합니다. `runserver`/임의 포트 실행 명령은 등록하지 않습니다.
10. 운영 환경변수로 `python manage.py check --deploy`를 실행하고 항목별로 해결합니다. 플랫폼 관리 화면에서 사이트를 재시작한 뒤 HTTPS·CSS·가입/로그인·금칙어·게시글·댓글·404를 확인합니다.
11. 사이트 ID에 대응하는 플랫폼 WSGI 로그와 관리 화면의 자원 사용량을 확인합니다. 계정의 실제 설정을 존중하며, 프로세스/스레드 수를 임의로 크게 늘리지 않습니다. 재시작 후 DB 자료 유지와 세션 동작도 확인합니다.

### 용량 관리와 복구

- 소규모 데모 데이터만 운영합니다. 자체 관리 목표는 디스크 할당량의 80% 미만과 메모리 한도 내 실행이며, 이는 플랫폼 보장 수치가 아닌 프로젝트 기준입니다. 한도를 넘으면 추가 기능보다 의존성·로그·데이터량을 먼저 줄입니다.
- 규칙 수는 초기 200개 이하, 전체 등록 상한은 500개를 제안합니다. 관리자/seed 경로 모두 같은 상한을 적용하고, 초과 시 기존 규칙을 보존하며 신규 추가를 거부합니다. 더 큰 목록은 성능 측정 후 별도 합의합니다.
- CSS와 템플릿 외 대형 자산, 이미지 라이브러리, 빌드 도구는 넣지 않습니다. 패키지 설치 캐시·중복 릴리스·대형 DB 덤프를 서버에 누적하지 않습니다.
- `python manage.py clearsessions`는 운영 환경변수를 주입해 플랫폼 예약 작업으로 정기 실행하는 절차를 문서화합니다. 예약 작업 사용 여부는 실제 계정에서 확인하며 미설정 시 수동 운영 절차를 제공합니다. 별도 상시 워커는 만들지 않습니다.
- 앱 로그는 민감정보를 제외하고 회전/상한을 정합니다. 플랫폼 로그와 앱 로그를 구분하며 계정 사용량에서 함께 점검합니다.
- 갱신 전에 코드 버전·의존성·DB 백업을 외부에 보관합니다. 플랫폼의 짧은 백업 보관만을 유일한 복구 수단으로 삼지 않습니다. 외부 보관은 접근 제한된 로컬 저장소로도 가능합니다.
- 실패 시 이전 코드/의존성을 복구하고 사이트를 재시작합니다. 스키마가 호환되지 않는 경우에는 쓰기를 중지한 상태에서 검증한 DB 백업을 복원하며, 백업 이후 작성 데이터가 유실될 수 있음을 기록합니다. 단순 코드 복귀가 DB 변경까지 되돌린다고 가정하지 않습니다.

| T15 / 배포 | 운영 WSGI·HTTPS·정적 파일 | DEBUG=False에서 CSS와 주요 기능 정상, 호스트 제한, HTTPS 루프 없음 |
| T16 / 영속성·복구 | 재시작·변경 배포 | DB 자료 유지, seed 자동 재등록 없음, 백업 복원은 격리된 로컬 환경에서 확인 |
| T17 / 자원 | 실제 alwaysdata 사용량 | 데모 조회/작성 후 메모리·디스크 계정 한도 내, 측정 시점·값 기록 |

자동 테스트 DB는 **로컬 PostgreSQL의 별도 DB**로 구성합니다. alwaysdata의 운영 DB로 테스트하거나 운영 계정에서 테스트 DB 생성 권한을 요구하지 않습니다. 브라우저에서는 가입→로그인→글 작성→댓글→규칙 추가→마스킹 확인→수정→삭제→로그아웃 흐름과 빈 화면·입력 실패 화면을 확인합니다. 세션은 브라우저 종료 만료를 기본 제안으로 하고 로컬 환경과 운영 환경의 Secure 쿠키 설정을 구분합니다.

## 9. 위험과 향후 변경 지점

- 현재 비밀번호 해시 적용 여부는 P0에서 합의가 필요합니다. 미합의 상태에서 평문 저장으로 대체하지 않습니다.
- 실제 계정 한도·Python 호환성·DB 접속값·도메인은 배포 전에 확인해야 합니다. 계정 접근이 없으면 P8까지 준비하고 P9를 배포 완료로 기록하지 않습니다.
- 물리 삭제는 복구 기능이 없습니다. 복구가 필요하면 P2 이전에 논리 삭제와 인덱스/조회 조건을 재설계합니다.
- 키워드 부분 일치는 오탐과 미탐이 있습니다. 최초 목록을 작게 시작하고 관리자 삭제로 조정하며, 완전한 유해 표현 탐지를 보장하지 않습니다.
- 원문 보관과 작성자 편집 원문 조회는 권한 통제 및 보관 정책이 필요합니다. 로그에는 게시글 원문을 불필요하게 남기지 않습니다.
- SNS 확장은 내부 회원 ID에 외부 제공자/식별자를 연결하는 별도 모델을 추가하고 계정 연결 정책을 결정합니다.
- 실제 비밀번호 복구는 Mock 화면의 처리 경계를 교체하고 만료 토큰·메일·재사용 방지·계정 노출 방지를 설계합니다.
- REGEX와 규칙 캐시 도입은 별도 단계로 처리합니다. 정규식 실행 제한, 캐시 무효화와 금칙어 변경 반영 검증을 추가합니다.
