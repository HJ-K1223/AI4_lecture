# note-demo 설계용 AI 에이전트 프롬프트

아래 "프롬프트" 섹션 전체를 AI 에이전트에 전달하세요. `{}` 로 표시한 부분은 사용 전에 직접 채워야 합니다. 사용 팁은 이 파일 맨 아래에 있습니다.

---

## 프롬프트

````markdown
# 역할
당신은 시니어 풀스택 아키텍트입니다. 아래 요구사항을 기반으로 "note-demo" 프로젝트의 **설계 문서**를 작성합니다. 이 단계에서는 구현 코드가 아니라 설계가 산출물입니다.

# 프로젝트 개요
- 프로젝트명: note-demo
- 성격: 회원 기반 게시판 데모 서비스
- 목적: 현재는 데모/MVP이며, 아래 "향후 확장 항목"을 쉽게 적용할 수 있는 구조여야 합니다.

# 기술 스택
- 백엔드: {예: Spring Boot 3 / Java 21}
- 프론트엔드: {예: React / Thymeleaf / 미정}
- DB: {예: H2(개발) → PostgreSQL(운영)}
- 미정 항목은 선택지 2~3개를 장단점과 함께 제시하고, 하나를 추천해 주세요.

# 기능 요구사항 (원문 그대로 반영, 임의 삭제·축소 금지)

## 1. 회원 가입
- 입력 항목: 이메일 주소, 이름(닉네임), 비밀번호
- 향후 SNS 로그인으로 대체될 예정 → 인증 로직을 분리하여 교체 가능한 구조로 설계
- 비밀번호는 향후 암호화 예정 → 비밀번호 처리를 단일 컴포넌트(예: PasswordEncoder 인터페이스)로 격리
- 이메일 중복 검증, 입력값 검증 규칙을 정의

## 2. 로그인 / 3. 로그아웃
- 인증 방식(세션 or JWT)을 선택하고 근거를 제시

## 4. 비밀번호 찾기
- 현재는 **Mock-up만 제공** (실제 메일 발송·재설정 로직 구현 안 함)
- 화면/API는 존재하되 고정된 안내 응답을 반환
- 향후 실제 구현으로 교체할 수 있도록 인터페이스만 정의

## 5. 게시판
- 게시글은 **제목**과 **내용**으로 구성
- 목록 조회에는 **제목만** 노출 (내용 제외, 작성자·작성일 노출 여부는 가정으로 명시)
- 5-1. 페이징 조회: 한 페이지 기본 10개 (page, size 파라미터, size 기본값 10)
- 5-2. 상세 조회: 제목, 내용, 댓글 확인
- 5-3. **본인 글만** 수정/삭제 가능 (서버 측에서 권한 검증)
- 5-4. 댓글 기능 (작성, 조회, 삭제 등 범위를 명시)
- 5-5. 불쾌한 표현 마스킹
  - 키워드 매핑 또는 정규식 방식으로 탐지 후 마스킹(예: `***`)
  - 5-5-1. 금칙어 목록
    - 최초 목록은 인터넷 등 최신 정보를 참고해 구성
    - **관리자가 금칙어를 추가/삭제**할 수 있어야 함
    - 금칙어는 코드에 하드코딩하지 않고 DB 등 데이터로 관리

# 설계 시 반드시 결정하고 근거를 적을 사항
1. 마스킹 시점: 저장 시 vs 조회 시 (원문 보존 여부, 금칙어 변경 시 소급 적용 여부 관점에서 비교)
2. 마스킹 대상: 게시글 제목·내용, 댓글, 닉네임 포함 여부
3. 금칙어 매칭 방식: 단순 포함, 정규식, 띄어쓰기·특수문자·자모 분리 우회 대응 수준, 성능 고려
4. 관리자 개념: 원문에 관리자 계정/권한 설계가 없으므로 최소 방식(예: role 컬럼)을 제안
5. 삭제 방식: soft delete vs hard delete, 게시글 삭제 시 댓글 처리

# 원문에 없는 사항 처리 규칙
- 요구사항에 없는 기능은 **추가하지 말고** "가정 및 확인 필요 사항" 섹션에 따로 정리
- 모호한 부분은 임의로 확정하지 말고, 가정(Assumption)을 명시한 뒤 진행
- 향후 확장 항목(SNS 로그인, 비밀번호 암호화, 비밀번호 찾기 실구현)은 **이번 범위 밖**이지만 확장 지점은 설계에 반영

# 금칙어 초기 데이터 작성 지침
- 웹 검색이 가능하면 신뢰할 수 있는 출처를 참고해 작성하고 출처를 기록
- 웹 검색이 불가능하면 대표적인 소수의 예시만 넣고, "출처 보강 필요"로 표시. 기억에 의존해 방대한 목록을 지어내지 말 것
- 초기 데이터는 코드가 아닌 seed 파일(SQL/CSV/JSON)로 분리

# 산출물 (아래 순서와 목차를 지켜 주세요)
1. 요구사항 정리표: 원문 항목 번호(1~5-5-1)별로 "반영 방법"을 매핑 (누락 여부 검증용)
2. 가정 및 확인 필요 사항
3. 시스템 아키텍처 및 기술 스택 결정
4. 도메인/데이터 모델: ERD(Mermaid), 테이블 정의(컬럼, 타입, 제약조건, 인덱스)
5. API 명세: 엔드포인트, 메서드, 요청/응답, 상태코드, 인증·권한 요구사항
6. 화면 목록 및 흐름 (회원가입, 로그인, 비밀번호 찾기 mock, 목록, 상세, 작성/수정, 관리자 금칙어 관리)
7. 핵심 로직 설계: 인증/권한 검증, 페이징, 마스킹 처리 흐름
8. 확장 계획: SNS 로그인, 비밀번호 암호화, 비밀번호 찾기 실구현 시 변경 지점
9. 보안·예외 처리 기준: 입력 검증, 권한 오류, XSS/SQL Injection 방어, 오류 응답 형식
10. 구현 순서 제안: 단계별 마일스톤과 테스트 포인트

# 진행 방식
- 먼저 요구사항 정리표와 가정 사항만 제시하고, 확인이 필요한 질문이 있다면 최대 5개까지 묶어서 물어봅니다.
- 질문이 없거나 제가 "그대로 진행"이라고 답하면 나머지 산출물을 작성합니다.
- 모든 산출물은 한국어로 작성하고, 코드·식별자는 영어를 사용합니다.
````

## 사용 팁

- `{}` 로 표시한 기술 스택은 꼭 채우세요. 비워 두면 에이전트가 스택부터 새로 고르느라 설계가 흔들립니다.
- 구현까지 맡기려면 "산출물"을 "이 설계를 기반으로 단계별로 구현"으로 바꾸되, 설계 승인 후 구현하는 2단계 방식이 정확도가 높습니다.
- 마스킹 시점(저장 시 vs 조회 시)과 관리자 계정 생성 방식은 원문에 결정 사항이 없어서, 일부러 "에이전트가 선택하고 근거를 적도록" 열어 두었습니다. 이미 정한 방향이 있다면 프롬프트에 못 박아 두는 편이 좋습니다.
- 금칙어 초기 목록은 에이전트의 웹 검색 가능 여부에 따라 품질이 크게 달라지므로, 검색이 안 되는 환경이라면 별도로 출처 있는 목록을 제공하는 것을 권장합니다.
